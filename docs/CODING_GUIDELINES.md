# Coding Guidelines

Цей документ описує стандарти написання коду для проекту. Дотримання цих правил є обов'язковим для збереження цілісності, читабельності та підтримуваності кодової бази.

## 1. Загальні принципи

- **Python Version**: Проект розрахований на Python 3.10+.
- **Type Hinting**: Використання анотацій типів є обов'язковим.
  - Використовуйте `typing` (`List`, `Dict`, `Optional`) або синтаксис `str | None`.
- **Linters**: Код повинен відповідати стандартам `flake8`.
- **Docstrings**: Публічні модулі, класи та функції повинні мати docstrings, що пояснюють їх призначення, аргументи та значення, що повертаються.

## 2. Архітектура та Модульність

Проект розділений на кілька ключових модулів, кожен з яких має свою зону відповідальності. **Змішування логіки між ними заборонено** без вагомих причин.

- **`app/admin_bot/`**: Адміністративна панель, управління користувачами, налаштування системи.
- **`app/watch_bot/`**: Основний бот для взаємодії з кінцевими користувачами.
- **`app/notificator_bot/`**: Сервіс розсилки повідомлень та сповіщень.
- **`app/sheet_bot/`**: Інтеграція з Google Sheets (експорт/імпорт даних).
- **`app/DAL/`**: Data Access Layer. Єдина точка доступу до БД.
- **`app/services/`**: Спільна бізнес-логіка, яку можуть використовувати різні боти.

## 3. Структура та Розмір Файлів (SRP)

- **Single Responsibility Principle (SRP)**: Один модуль = одна відповідальність.
- **Розмір файлів**: Якщо файл перевищує **300–400 рядків**, це сигнал до рефакторингу. Розбивайте великі файли на менші логічні модулі.

## 4. Стиль коду та Іменування

- **Змінні та функції**: Використовуйте `snake_case`.
- **Повні назви**: Назви змінних мають бути повними та описовими.
  - ✅ `user_id`, `channel_title`, `message_text`
  - ❌ `uid`, `ch_ttl`, `msg`
- **Класи**: `CamelCase` (наприклад, `Channel`, `MembershipDAO`).
- **Константи**: `UPPER_CASE` (наприклад, `MAX_RETRIES`).

## 5. Робота з Базою Даних (DAL)

- **Повернення об'єктів**: Методи DAL мають повертати ORM-об'єкти (або Pydantic-моделі), а не "сирі" кортежі чи словники.
- **ORM**: Використовуємо SQLAlchemy Session.
- **Сесії**: Сесія відкривається на рівні сервісу/хендлера і передається в DAL. Не відкривайте сесію всередині циклів.

## 6. Обробка помилок (Exceptions)

- **Явні типи помилок**: Використовуйте та створюйте специфічні класи помилок для бізнес-логіки.
  - ✅ `raise OwnerConflictError("...")`, `raise ExternalRateLimit("...")`
  - ❌ `raise Exception("bad")`
- **Структура try/except**: Блок `try` має охоплювати логіку, а `except` — обробляти конкретні помилки в кінці.
- **Логування**: При перехопленні помилок використовуйте `log.exception` або `log.error(..., exc_info=True)`.

## 7. Конфігурація та Безпека

- **Secrets**: Ніколи не хардкодьте токени, паролі чи ключі API. Використовуйте змінні оточення (`.env`).
- **Config**: Доступ до конфігурації має здійснюватися через централізовані модулі конфігурації (наприклад, `app/config.py`).

## 8. Повторне використання коду (DRY)

- **Перевірка перед написанням**: Перед створенням нової функції чи утиліти, **обов'язково** перевірте, чи не існує вже схожої реалізації в проекті.
- **Пріоритет існуючого**: Використання існуючих, протестованих функцій є пріоритетним.

## 9. Асинхронність та Логування

- **AsyncIO**: Не блокуйте Event Loop синхронними викликами (наприклад, `time.sleep`).
- **Logging**:
  - Використовуйте `logging.getLogger(__name__)`.
  - Заборонено використовувати `print()`.

## 10. Час та часова зона

- **Єдина TZ**: Використовуємо лише `Europe/Moscow` через утиліту `app.utils.time_utils`.
- **Функції**: Для поточного часу беріть `moscow_now()`, рядок часу — `moscow_now_str()`, tz-aware datetime — `MOSCOW_TZ` або `ensure_moscow_timezone(...)`.
- **Заборонено**: `datetime.now()`, ручне створення `ZoneInfo("Europe/Moscow")` або власні формати часу поза `time_utils`.
